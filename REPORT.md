# Теоретическая часть

## Нужны ли стайлгайды

Стайлгайд обеспечивает единообразие и стандартизирует оформление документации. Зафиксированные правила уменьшают разночтения и количество ошибок, ускоряют подготовку новых страниц и помогают нескольким авторам работать согласованно. Новому участнику проще понять принятые решения, а читателю — искать и воспринимать информацию в документах с предсказуемой структурой.

Отдельный большой стайлгайд нужен не всегда. Для небольшого проекта с одним автором достаточно нескольких зафиксированных договорённостей. По мере роста проекта, объёма документации и количества авторов ценность полноценного руководства увеличивается.

## Использование стайлгайда при разработке документации

Автор сверяется со стайлгайдом при выборе уровней заголовков, структуры страницы, терминов и тона изложения. Руководство также задаёт оформление пошаговых инструкций, списков, таблиц, ссылок, изображений, команд, имён файлов, элементов интерфейса, предупреждений, примечаний и примеров кода. Благодаря этому не приходится каждый раз заново принимать одинаковые оформительские решения.

Например, последовательные действия оформляются нумерованным списком, команда `mkdocs serve` — как inline code, а ссылка получает описательный текст. Термин «учётная запись» не заменяется случайным образом словами «аккаунт» или «профиль».

## Использование искусственного интеллекта

ИИ может проанализировать существующие документы, найти повторяющиеся паттерны и несогласованную терминологию, а затем предложить первоначальный набор правил. Его также можно применять для поиска противоречий между правилами, проверки новых страниц на соответствие стайлгайду, улучшения неясных формулировок и подготовки предложений при расширении руководства.

Результат работы ИИ должен проверять человек. Модель может предложить неподходящее правило или неверно интерпретировать контекст проекта, поэтому автор отвечает за окончательное решение.

# Исходные данные

Цель учебного стайлгайда — сделать техническую документацию веб-приложения единообразной, понятной и удобной для поддержки.

Руководство охватывает пользовательские инструкции, инструкции для разработчиков, справочные страницы и страницы с примерами использования. Авторы — разработчики и технические писатели; читатели — пользователи и разработчики. Для работы применяются Markdown, MkDocs, Git и GitHub.

Стайлгайд должен предотвращать разные названия одной сущности, неинформативные заголовки, слишком длинные предложения, неодинаковое оформление команд и файлов, непоследовательные инструкции, неясные тексты ссылок, перегруженные примеры кода и разнородную Markdown-разметку.

В реальном проекте на этом этапе дополнительно анализировались бы существующие документы и практики команды. Интервью и исследование организации в этой учебной работе не проводились.

# Изученные примеры

Перед составлением правил были кратко рассмотрены предложенные в лекции примеры: [Google Developer Documentation Style Guide](https://developers.google.com/style), [стайлгайд Ozon](https://docs.ozon.ru/styleguide/) и материалы о разработке Content Style Guide из презентации. Они помогли оценить возможную структуру руководства и уровень конкретности правил; большие фрагменты источников не копировались.

# Структура правил

Руководство регулирует общие принципы документации, стиль изложения, орфографию и пунктуацию, терминологию, структуру документов, заголовки, абзацы, списки и пошаговые инструкции. Отдельные правила относятся к Markdown, ссылкам, изображениям, командам и именам файлов, элементам интерфейса, примечаниям, предупреждениям, примерам кода и доступности текста.

Эти вопросы влияют на понятность, последовательность и проверяемость документации. Структурные правила помогают быстро находить сведения, языковые — правильно понимать их, а правила разметки сохраняют предсказуемое отображение страниц.

# Структура стайлгайда

- «Общие принципы» определяют понятность, краткость, единообразие и актуальность.
- «Язык и стиль» содержит правила тона, формулировок, орфографии и пунктуации.
- «Структура документа» описывает страницы, заголовки, абзацы, списки и инструкции.
- «Оформление» задаёт правила Markdown, ссылок, изображений и элементов интерфейса.
- «Примеры кода» регулирует inline code, блоки кода и команды.
- «Терминология» фиксирует основные названия сущностей.
- «Доступность текста» содержит правила для заголовков, ссылок, изображений, сокращений и элементов интерфейса.

# Тестирование стайлгайда

## Как запустить приложение локально

Результат: учебное приложение доступно в браузере.

Предварительное условие: установлены Python и зависимости проекта.

1. Откройте терминал в каталоге проекта.
2. Установите зависимости командой `python -m pip install -r requirements.txt`.
3. Запустите приложение:

   ```powershell
   python app.py
   ```

4. Откройте в браузере адрес `http://localhost:8000`.
5. Убедитесь, что появилась главная страница учебного приложения.

## Как изменить пароль

Результат: для учётной записи установлен новый пароль.

1. Откройте **Настройки**.
2. Выберите раздел **Безопасность**.
3. Введите текущий пароль в поле **Текущий пароль**.
4. Введите новый пароль в поле **Новый пароль**.
5. Нажмите **Сохранить**.
6. Выйдите из приложения и войдите с новым паролем.

# Оценка качества стайлгайда

В примерах применены информативные заголовки, краткие предложения, последовательные шаги, единая терминология, inline code и единое оформление элементов интерфейса. Правила упростили выбор структуры и помогли оформить две разные инструкции одинаково. Наиболее полезными оказались требования «одно действие — один шаг» и единые названия сущностей.

Текущего объёма достаточно для небольшой учебной документации, но руководство не решает все возможные задачи. В большом проекте потребовалось бы расширить глоссарий и добавить правила для API-справочника, сообщений об ошибках и других специфических видов документации.

# Процесс разработки стайлгайда

1. В качестве исходных данных зафиксированы цель, авторы, читатели, виды документов и типичные проблемы.
2. Сформирована структура правил.
3. Кратко изучены внешние примеры стайлгайдов.
4. Написаны конкретные правила и распределены по страницам.
5. Правила проверены на двух учебных инструкциях.
6. Руководство подготовлено к публикации с помощью MkDocs.
7. Раздел «Доступность текста» был добавлен в отдельной ветке и представлен в Pull Request. Другой студент провёл review и оставил замечания.
8. По замечаниям уточнено правило об использовании цвета, добавлен Markdown-пример декоративного изображения с пустым alt-текстом и конкретизировано правило о расшифровке сокращений. После правок выполнены повторные проверки и создан отдельный commit.
9. После завершения review Pull Request был объединён с `main`. Автоматический deployment проверен: обновлённый раздел опубликован вместе с остальным стайлгайдом.
